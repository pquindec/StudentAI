Good morning everyone. Today we are going to talk about database transactions and why they matter for almost every application you will build. A transaction is a group of operations that the database treats as a single unit of work. Either all of the operations succeed, or none of them do. The classic example is a bank transfer. If we subtract one hundred dollars from Alice and then the server crashes before we add those hundred dollars to Bob, the money simply disappears. Transactions exist to prevent exactly that kind of problem.

We usually describe the guarantees of a transaction with the acronym ACID. A stands for atomicity, which is the all or nothing property I just described. C stands for consistency, meaning that a transaction moves the database from one valid state to another valid state, respecting every constraint we have defined, such as foreign keys or unique columns. I stands for isolation, which means that concurrent transactions should not see each other's intermediate results. And D stands for durability, which means that once a transaction has been committed, it will survive a power failure or a crash.

Isolation is the property that causes the most confusion, so let us spend some time on it. Running every transaction one after another would be perfectly isolated, but it would also be very slow. So databases offer several isolation levels, which trade correctness for performance. The weakest common level is read uncommitted, where a transaction can see changes that another transaction has not committed yet. This leads to what we call dirty reads. The next level is read committed, which is the default in PostgreSQL. Here you only see committed data, but if you read the same row twice you might get two different values, because another transaction committed in between. That is called a non repeatable read.

Repeatable read fixes that problem. Once you have read a row, you will keep seeing the same version of it until your transaction ends. However, under the formal definition, you can still suffer from phantom reads, where a query that returns a set of rows returns additional rows the second time you run it. Finally, serializable is the strongest level. It guarantees that the result is the same as if the transactions had run one at a time in some order. The cost is that the database may abort some of your transactions, and your application must be ready to retry them.

How do databases actually implement isolation? There are two main families of techniques. The first is locking. Before reading or writing a row, a transaction acquires a lock on it, and other transactions must wait. Two phase locking is the traditional approach. The second family is multi version concurrency control, usually called MVCC. Instead of overwriting a row, the database keeps several versions of it, and each transaction reads the version that was valid when it started. Readers never block writers and writers never block readers. PostgreSQL, Oracle and MySQL with the InnoDB engine all use some form of MVCC.

Locks bring their own problem, which is the deadlock. Imagine transaction one locks row A and then wants row B, while transaction two has already locked row B and now wants row A. Neither can continue. Databases detect this situation automatically and kill one of the two transactions. As developers, we can reduce deadlocks by always accessing rows in the same order and by keeping our transactions short.
